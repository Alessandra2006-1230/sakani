### Current database schema

- `users`: full name, email, password hash, salt, creation timestamp.
- `categories`: name and income/expense type.
- `transactions`: user ID, category ID, type, amount (`DECIMAL(12,2)`), description, transaction date, creation timestamp.
- Foreign keys link transactions to users and categories.
- The schema includes a positive-amount check constraint.
- User deletion cascades to that user's transactions.

### Important audit findings and cautions

- `config.py` contains database connection credentials in source code. Do not repeat or commit real passwords in new files. Move secrets to environment variables or a local ignored configuration file while retaining a safe example configuration.
- The README says the application is configured for port `3307`; the user's current successful MySQL server is on port `3306`. Make the port configurable and document the actual local setting. Do not blindly overwrite working local settings.
- `categories` appears to be a global table, not explicitly owned by a user. Review category seeding and queries before changing the schema.
- Existing transaction records do not include a crop, farm plot, production cycle, yield, or harvest linkage.
- No test suite was visible in the archive. Add automated tests for business logic and SQL query behavior where practical.
- The archive includes `__pycache__` directories. Keep generated bytecode, virtual environments, local secrets, logs, and database dumps out of source control.
- Do not assume the app supports cloud sync, online services, live weather, notifications, mobile access, inventory, or crop profitability. Those are proposed additions, not current capabilities.
- Avoid destructive database resets. Existing user accounts and transactions must be preserved.

## 2. Product vision

Sakani should remain a **local-first farm financial management desktop application**. Its primary job is to help a farmer record financial activity and understand the costs, revenue, and profitability of farm operations.

### Product principles

1. **Simple for real users:** clear labels, plain language, helpful validation, minimal clutter.
2. **Agriculture-specific:** crop and production-cycle accounting should differentiate it from a generic personal expense tracker.
3. **Accurate before flashy:** all financial totals must come from validated database queries and be mathematically correct.
4. **Offline-first:** all essential functions work without internet.
5. **Data-safe:** no destructive migrations, no cross-user data leakage, no silent data loss.
6. **Lightweight:** suitable for a modest laptop; avoid large libraries and excessive background processes.
7. **Incremental:** improve the existing codebase rather than replacing it wholesale.

### Target users

Small farmers, household farm operators, and student demonstrators who need to keep farm income and expenses organized.

### Core value proposition

“Record farm finances, understand where money goes, and see which crop or production cycle is earning a return.”

### Phase 1 — Security, reliability, and core behavior (P0)

- Add a clear configuration error when required settings are missing.
- Use parameterized SQL for every query.
- Ensure every transaction read, update, and delete is scoped to the authenticated `user_id`.
- Validate email, required fields, positive finite monetary amounts, date values, category/type compatibility, and maximum text lengths.
- Use `Decimal` or database decimal values for money calculations; avoid binary floating-point arithmetic for financial totals.
- Handle connection errors, query failures, and duplicate email gracefully.
- Use transactions and safe rollback behavior for multi-step database changes.
- Confirm logout clears the current session and returns to login.
- Ensure a user cannot access another user's transaction by changing an ID.
- Add tests for password hashing/verification and core calculation functions.
- Add backup/restore guidance. Do not silently create or overwrite backups.

Acceptance criteria:
- Invalid input is rejected with a useful message.
- Users only see and modify their own records.
- Login and registration still work.
- The app does not crash on ordinary database failures.
- Existing data is retained.

### Phase 3 — Crop and production-cycle accounting (P1, flagship feature)

**Goal:** link financial transactions to a crop or production cycle so users can estimate profitability.

Proposed capabilities:
- Create and manage crop/production-cycle records.
- Example fields: crop name, variety (optional), plot/field label (optional), planting/start date, harvest/end date (optional), status, notes.
- Link an existing transaction to a production cycle where applicable.
- Allow general farm expenses that are not assigned to a crop.
- Record harvest sales as income transactions linked to the appropriate cycle.
- Provide a cycle detail page showing income, expenses, and net result.
- Filter transactions by cycle.
- Mark cycles as planned, active, harvested, or archived, using validated state transitions.
- Allow edits and deletion only with confirmation and clear consequences.
- Provide migration logic that leaves all old transactions valid and visible.

Suggested new table (adapt after reviewing the existing schema and queries):

`production_cycles`
- `id` primary key
- `user_id` foreign key to `users`
- `crop_name`
- optional `variety`
- optional `plot_name`
- `start_date`
- nullable `expected_harvest_date`
- nullable `actual_harvest_date`
- `status`
- optional `notes`
- `created_at`

Add nullable `production_cycle_id` to `transactions`, with a foreign key and an index. Existing transactions must remain valid with a `NULL` cycle ID.

Important:
- Do not invent agricultural recommendations or claim that estimated dates are guaranteed.
- This phase is financial tracking, not a crop-calendar engine.
- Do not add yield calculations until yield and units are modeled clearly.
- Do not allocate shared expenses across crops automatically unless the user explicitly enters and understands the allocation rule.

Acceptance criteria:
- A user can create, edit, view, and archive a production cycle.
- A transaction can optionally be linked to a cycle.
- Old transactions still display correctly.
- Cycle totals match the underlying transaction records.
- A cycle's net result equals linked income minus linked expenses for the selected date range.
- Another user cannot see the cycle or its transactions.

### Phase 4 — Reports and financial insights (P1)

Financial definitions:

Acceptance criteria:
- Dashboard and reports agree for the same period.
- Totals match independently calculated test data.

## 4. Database migration rules

Database changes must be additive and safe.

1. Back up the current database before migration.
2. Inspect the current live schema before applying migration statements.
3. Do not drop or recreate `sakani_db`, `users`, `categories`, or `transactions`.
4. Use explicit, repeatable migration scripts or idempotent migration checks.
5. Preserve user IDs, transaction IDs, amounts, dates, descriptions, and category references.
6. Add new foreign keys and indexes only after verifying existing data satisfies the constraints.
7. Keep existing transactions valid when new fields are introduced by allowing nullable values or a safe documented default.
8. Run migrations in a controlled order and report success or failure clearly.
9. If a migration fails, stop and provide recovery instructions; do not continue with a partially upgraded schema.
10. Never reset the developer's local database just to make a demo easier.
